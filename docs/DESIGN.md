# Interface design (phase 6)

Neutral, quiet aesthetic: lots of white space, a "blank sheet of paper" feel, a single typeface (Inter, self-hosted) and a black-and-white palette (charcoal accent `#2b2b2b`, inverted to near-white in the dark theme). Light and dark themes. Lightweight top navigation, no sidebar. Keyboard first (Ctrl+K opens the command palette). Primarily desktop use, adapted to mobile.

The visual reference is the six screens on the design canvas (`A1` notes, `A2` note states, `A3` Kanban, `A4` expenses, `A5` palette, `A6` mobile).

## When to use PrimeNG and when custom CSS

| Use **PrimeNG** (complex, accessible behavior already solved)        | Use **custom CSS** (what defines the identity or is very specific) |
| -------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `p-table`: sorting, filters, row selection, cell editing, pagination | Top bar, navigation, command palette (with capture)                |
| `p-select`, `p-multiselect`, `p-datepicker`: selectors and dates     | Notes canvas (cards, groups, dragging)                             |
| `p-dialog`, `p-confirmdialog`, `p-toast`: modals and notices         | Kanban board and its dragging                                      |
| `p-tooltip`, `p-checkbox`, `p-toggleswitch` when needed              | Calendar grid, cards, chips, simple buttons, simple forms          |

Rule of thumb: if you would have to reimplement keyboard handling, focus, ARIA and edge cases (tables, selectors, dialogs), use PrimeNG. If it is a visual piece of the design, use custom CSS with the tokens. **Do not mix**: a normal button is `.btn`, not `p-button`.

The PrimeNG configuration (`providePrimeNgTheme()` in `core/theme/provide-primeng.ts`) is declared in the `providers` of the **routes** that use it, never in `app.config.ts`: this keeps its theming engine in lazy chunks (the initial bundle goes from 574 to 358 kB). A new screen using PrimeNG adds that provider to its route.

Each component is imported individually (`import { TableModule } from 'primeng/table'`), never a general module. PrimeNG is already styled with the tokens (see `styles/_primeng.scss`), so it changes with the theme alone. PrimeNG colors are not overridden with loose values: adjust the matching `--p-*` variable in `_primeng.scss` or use a token.

## Tokens (`apps/web/src/styles/_tokens.scss`)

Colors: `--bg`, `--surface`, `--surface-2`, `--line`, `--line-strong`, `--text`, `--muted`, `--accent`, `--accent-hover`, `--accent-soft`, `--on-accent`, `--danger`, `--danger-soft`, `--success`, `--success-soft`, `--warning`, `--warning-soft`, `--overlay`.
Shape: `--radius-sm|md|lg|xl|pill`, `--shadow-sm|md|lg`, `--space-1…7` (4–48 px), `--text-xs…3xl`, `--control-height` (36 px), `--touch-target` (44 px), `--page-max`, `--page-gutter`, `--nav-height`.

**No loose colors, ever**: no `#fff`, no `rgb(...)` outside `_tokens.scss`. Everything uses `var(--token)`, so the dark theme works on its own. The theme is applied with `data-theme="light|dark"` on `<html>`; `@media (prefers-color-scheme)` is not used in components.

**Icons**: every screen uses Tabler Icons through `<app-icon name="…">` (`core/ui/icon.ts`), drawn inline as SVG at the size and color of the text. Only the icons in `core/ui/tabler-icons.generated.ts` ship: the ones a stock category can pick (`CATEGORY_ICONS` in `shared`) plus the interface ones listed in `apps/web/scripts/generate-tabler-icons.mjs`; after changing either list run `pnpm --filter @rayrecords/web icons:tabler`. PrimeIcons (`pi pi-…`) is only left where PrimeNG draws the icon itself: the warning of the confirmation dialogs and the buttons of `p-inputnumber`. Do not add new `pi` icons to a template. Size and color an icon from its parent (`font-size`, `color`), targeting the `app-icon` element or a class set on it.

**Categories** (stock and expenses alike) are an icon on a colored square, managed in one place: `features/categories/` holds the manager dialog (`<app-categories-dialog>`, list and editor side by side; the host gives it the data operations and the wording), the badge (`<app-category-badge>`) and the name with its badge (`<app-category-label>`, used wherever a category is named). Icons and color pairs are `CATEGORY_ICONS` and `CATEGORY_COLOR_PAIRS` in `shared`.

**Colors chosen by the user** are the one exception to "no loose colors": a stock category stores its own square and icon colors (`#rrggbb`) and `<app-category-badge>` paints them as they are, the same in both themes. The suggested ones are the pairs in `CATEGORY_COLOR_PAIRS` (`shared`): a square and an icon color that reads on it, picked together. A hovered table row uses `--row-hover`, lighter than the header (`--surface-2`), so a row never reads as a header.

A box that scrolls inside the page takes the `appScrollFade` directive (`core/ui/scroll-fade.ts`): it adds the global `.scroll-fade` mask and fades the top and bottom edges only while there is more content that way. Scrollbars are styled once, in `_base.scss` (thin, no track, token colors).

If a screen needs a piece that will be reused on another, add it here (and to this table); do not copy it between components.

## Dates, times and other controls

- **Date and time**: `<app-date-field>` and `<app-time-field>` (`core/ui/`). String value `YYYY-MM-DD` / `HH:mm`. On touch devices they use the system's native input; on desktop, `p-datepicker` (date) or a masked field (time). Never a bare `type="date"`. They require `providePrimeNgTheme()` on the route. Declare them with `<label for>` and `inputId`, not wrapped in a `<label>`.
- **Month or range picker**: `p-datepicker` with `[touchUI]` on touch devices.
- **Dropdowns**: `p-select`; **stepped numbers**: `p-inputnumber`; **checkboxes**: `p-checkbox` or the global style.
- **Tables**: `[rowHover]` only with a real pointer (`@media (hover: hover)`); done rows turn neutral gray.
- **Dragging on the canvas**: the card lifts (shadow and minimal scale, no rotation) and leaves a dashed mark in its place; transitions never affect `left`/`top`. Ctrl+Z undoes.
- **Notes: bounded canvas**: header and canvas use the `.page` column (same width and margins as the global header); only the height is kept (it fills what remains of the window) and the canvas has its own horizontal scroll. Box with a subtle border (inner shadow, so the cards' origin does not shift); when dragging something, the dashed outline of the zone is drawn; the shadow of a dragged group is contained (accent outline + `--shadow-md`). Nothing can be dragged or resized out of the visible box (right and bottom included): the limits are fixed when the drag starts, so dragging never grows the canvas, and a 8 px padding keeps the cards' borders visible against the edges.
- **Notes: header**: a single row on desktop, in this order: "Nueva nota" (new note) · "Ordenar" (sort; icon and text) · "Terminadas (N)" (done) · lock. Group (Ctrl+G) and mark done/reopen (X) have no header button: they live in the hint bar at the bottom, in the card's action bar and in their shortcuts. On mobile only "Terminadas" remains.
- **Notes: lock and sort**: the header lock (`aria-pressed`, locked by default, remembered in `rayrecords.notes.locked`) prevents moving cards and groups, resizing and the arrow keys; while locked you can still select, edit, group, delete and undo. A drag attempt shows the notice "Disposición bloqueada · Desbloquea para mover" (layout locked · unlock to move). When unlocked, dragging starts at 8 px. "Ordenar" rearranges loose cards and groups into a grid (reading order, no overlaps) as a single undoable operation.
- **Focus and selection on cards**: a single border. Selection is the 2 px accent border; keyboard focus is drawn inside the border (inner double line), never as an outer ring (the global `outline` is cancelled on the host with `:host(:focus-visible)`).
- **Global keyboard**: Shift+N / L / C / G / U go to Notes, Lists, Calendar, Expenses and Accounts (they do nothing with focus in a field, selector or calendar, with a modal open or with Ctrl/Alt/Meta; in notes, a bare "N" creates a card). "/" outside a field opens the palette in "Nueva nota o tarea" (new note or task) mode (also from the palette's top row, for touch): you type there, e.g. compra: leche, with a preview of the target list; Enter saves and Esc clears or exits. Alt+← / Alt+→ cycle through the sections (Notes, Lists, Calendar, Expenses, Accounts), without wrapping around, and replace the browser's back/forward. That is why no screen uses Alt+arrows; in notes, Shift+arrows moves the selection.
- **Loading skeletons**: while data arrives for the first time, `.skeleton` blocks (`.line`, `.title`, `.pill`, `.circle`, `.block`) are drawn with the same dimensions as the real content, so nothing jumps: `app-notes-skeleton` (cards and a ghost group inside the canvas box; rows on mobile) and `app-lists-skeleton` (`grid`, `table` and `board`). The blocks carry `aria-hidden="true"` and a `role="status"` with the `.sr-only` class announces the loading. They appear after a 150 ms delay done with `animation-delay` in CSS (no timers): a fast load never shows them. The empty state is shown only after loading, never as a substitute for the skeleton.
- **Expenses layout**: four views as tabs in the page header, on the title's row (a row of their own on a phone): Movimientos, Revisar, Importar and Reglas; the old Resumen is gone, its figures live in Movimientos. Movimientos has two columns: on the left a filter band (the period picker, whose popover alone moves between months and years with no arrows, the grouping toggle "Agrupar por comercio" and the text search filling the rest; the categories are filtered from the summary), the three figures of the period as cards (Balance, Gastos, Ingresos) and the table under them; on the right (a desktop) the **Resumen**: its name with the count of movements of the period on top, the category list (badge, name, amount and a bar against the largest one, no movement counts; "Todas" is a card like the others, with the look chosen in the category manager; ordered from the largest amount to the smallest with "Sin categoría" and its own badge last; only categories with movements in the period, the chosen one stays even if empty), which also filters the table and scrolls inside its card when it does not fit, closed by a rule and the "Categorías" button that opens the category manager, and at the foot Importar and Reglas side by side and, under them, the `.alert.warning` shortcut "N sin categoría · Revisar" (shown only when something is pending). The summary never grows past the window, so the foot is always in view. On a phone the summary's header and Importar/Reglas are not drawn (the tabs do that job); only the review shortcut stays, and the figures become one band right under the filters (the balance big, expenses and income beside it). With a category chosen the table is titled with its name and how many movements it holds ("Hogar · 8 movimientos"); with none it is only read aloud on a desktop. A row shows the category as in Stock (badge and name, no container) and ends with a pencil that opens `app-movement-dialog`: the bank data read only and a category select with icons (no rule is created from here). The summary stays in view while the table scrolls; on a phone the categories are a row that scrolls sideways. The movements come as a feed: with the table sorted by date and not grouped (how it starts), each day opens with a band (`tr.day-row`, a row group of the table) with its date ("Viernes 20 nov") and what the day adds up to, and the date is no column; sorting by another column gives the plain table with its date column back. The table title is read aloud only on a desktop. The "Agrupar por comercio" toggle (off from the start) (icon only on a phone) lists one row per normalised description instead: its movement count, summed amount and category ("Varias" when they differ), with a chevron button (`aria-expanded`) that opens the place to show each of its movements; filters apply before grouping and the paginator counts groups. When a category (or "Sin categoría") is chosen on the left, the Categoría column is dropped, since it is implied.
- **Switching expenses views**: changing tab shows `app-expenses-skeleton` for 300 ms, drawn for that tab's content (movements, review, import or rules; a simulated load, skipped with `prefers-reduced-motion`) and then fades the view in.
- **Header**: it takes `--nav-bg` and `--nav-fg`, a soft tone close to the page background (light grey in the light theme, dark grey in the dark one) with a bottom border like the rows', so only the buttons carry the strong contrast.
- **Theme**: the default is the light theme. The header toggle picks light or dark and saves the choice in the user's account (`theme` on the user: `system`, `light` or `dark`; `light` until one is chosen), so it comes back on every device. `system` is still accepted for accounts that had it, but the menu no longer offers it. The browser keeps a copy in `localStorage` (`rayrecords.theme`) only so `theme-init.js` can paint the right theme before the session is known; the account is what decides.
- **Header on a phone** (under 768 px): tapping the brand opens a menu with the theme toggle and logout, so the search field takes the whole first row.
- **Installable app**: `public/manifest.webmanifest`, the icons in `public/icons` and a minimal `public/sw.js` (it caches nothing; it only makes the app installable). The logo is `public/logo.svg` (a white manta ray on a charcoal disc, two flat colours; the header and the login page use it as an image). The icons are generated from it: after changing the logo, regenerate them with `pnpm --filter @rayrecords/web icons`.
- **Reorderable lists**: drag handle and "Mover antes/después" (move before/after) buttons on each card (on touch, only the buttons); the order is saved in `order`.
- **Page scroll**: the two header rows never scroll. The shell is as tall as the window and only its `<main>` scrolls, so the scrollbar starts under the header; the window itself never scrolls (`window.scrollY` is always 0: use `pageScrollTop()` from `core/ui/page-scroll.ts`). `position: sticky` offsets inside a screen are measured from the top of `<main>`, not of the window. Changing screen puts the scroll back at the top.
- **Header**: the content aligns with the page width; brand on the left, navigation centered, actions on the right. On mobile, two rows with swipeable navigation.

## Component structure and styles

- Semantic HTML template: `button` for actions, `a` for navigation, a `label` linked to every control, a single `h1` per screen. No clickable `div`s.
- Own styles in the component's `styles:` (or a `.scss` next to it), with tokens and the global classes. No `!important`, no inline styles except dynamic values (positions, widths).
- Focus always visible (already defined in `_base.scss`); 44 px touch targets on mobile; sufficient contrast (the tokens already meet it).
- Mobile: below 768 px the screen must remain usable without horizontal page scroll. Wide tables scroll inside their box.
- Keyboard first: everything important is reachable without a mouse.

## How a screen is verified

1. `pnpm --filter @rayrecords/web test` passes.
2. It builds: `pnpm --filter @rayrecords/web exec ng build --output-path <temporary folder outside the repo>`.
3. It is tested in the browser, with a dedicated seeded database (never the user's development one), in light and dark, at desktop and mobile (375 px) widths. No console errors.
4. It is compared with the matching design screen and with its real functionality (what the design shows must be doable).

- **Scroll and header tabs**: the shell is as tall as the window and `<main>` is the only scroller (`html` is `overflow: hidden`, and `main` is the containing block of `.sr-only` content so it cannot stretch the document), so no scrollbar runs next to the two header rows. A tab never changes width when it becomes active: a hidden copy of its text in the bold weight (`.tab-text::after`) reserves the room, and the bar under it is a pseudo-element that fades and grows instead of a border that pops in.
- **Stock layout**: the screen fills the space under the header. The table area is what is left between the toolbar and the bottom pager; the page size is measured from it (`fitPageSize`, with a `ResizeObserver`): as many rows as fit, never fewer than five. The card always takes the whole area, empty space included, so the page navigation under it (a centered `p-paginator` outside the card) never moves from one page to the next. The count and the total stock (units and value) are at the top right of the toolbar. The filters float under their button (`.filters-wrap`) and close on an outside click or Escape, so opening them never changes the height of the table. On a short window the page scrolls a little rather than going under five rows; on a phone the page scrolls as usual, with 20 rows per page and the filters inline.

- **Container radius**: the big containers of Notes (canvas and frame) and Lists (cards and tables) share `--radius-container` (14 px), so changing tab never makes their corners jump; the note cards inside keep `--radius-md`.
- **Expenses grouping**: movements start grouped by description. A group is a plain row (no background) whose first cell holds the open/close indicator, with its movement count and no date; the whole row opens it. Its movements hang under it with their date in a cell that spans the date and description columns (the description only shows if it is written differently) and their amount and their own category, always, so each movement of a place can be moved on its own (its pencil, or the selection for several). Every place is a group, a single movement included. The "Agrupar" button next to the filter cross-fades between its two icons (`list` and `stack-2`) when toggled.
- **Receipts**: a ticket prints as a receipt sized to a thermal roll (80 mm by default, 58 mm optional): plain black on white in a monospace font, the shop texts above (only the filled ones), one block per line with its quantity, unit price and total, then the total and the unit count. It is drawn from the `Receipt` model in `shared`, so any other printer would draw from the same data. "Editar ticket" (toolbar of Tickets) opens a dialog with a preview made from a sample ticket: the logo (an image scaled to 384 px wide and turned grey, kept as a PNG data URL), the title, the address and shop data, the tax id, the closing line and the roll width, all kept in the browser. In Ventas the footer button "Imprimir ticket" creates the ticket, prints it and empties the cart, staying on the sale with a notice that links to the ticket; if creating it fails nothing prints and the cart stays.
